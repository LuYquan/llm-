# ADR 0004: 急停是「使用者配置的发送槽位」，而不是软件内置的停机动作

- **状态 (Status)**: 已接受 (Accepted)
- **日期 (Date)**: 2026-09-22
- **决策人 (Deciders)**: 产品负责人（用户）
- **相关**: `CONTEXT.md`（`EmergencyStop` 术语）、[ADR 0001](0001-hybrid-workbench-layout-and-session-model.md)、上位机 v1 计划 `V1_EXECUTION_PLAN.md`

## 1. 背景与问题陈述 (Context)

两处决定存在冲突：

1. **基准术语表**把 `EmergencyStop` 定义为"全局最高优先级中断（空格键触发），瞬间向单片机下发停机指令或重置控制器输出"，即软件内置的停机动作。
2. **2026-09-21 的明确决定**是"删掉所有停机/急停逻辑：设备侧安全由硬件负责，停机指令由用户在指令表里自配"。

同时存在不可回避的物理事实：目标设备的串口**没有回执保证**，没有独立看门狗，也没有物理急停。
在这种前提下，把"急停"做成一个软件内置动作，会制造**虚假的安全感**——操作者按下按键后可能以为设备已停，而字节是否送达、设备是否响应都未知。

## 2. 备选方案权衡 (Alternatives & Trade-offs)

### 方案 A：软件内置停机动作（按基准字面实现）

- 优点：开箱即用，一个键就能停。
- 缺点：软件并不知道设备的停机指令是什么（每台硬件不同），只能猜或写死；在无回执链路上无法证明停机生效，虚假安全感风险最高。

### 方案 B：完全不做任何停机入口（坚持 9/21 决定）

- 优点：绝不让软件介入安全动作，责任边界最清晰。
- 缺点：与基准的最高优先级中断能力不符；用户在急迫时反而只能去操作串口助手或拔电，丢失一个已知可用的救济手段。

### 方案 C（选定）：空格键作为 **保留的高优先级发送槽位**，内容由使用者配置

- 优点：
  - 与 9/21 决定一致（软件不内置任何设备特定命令）；
  - 与基准一致（空格键仍是全局最高优先级发送）；
  - 责任清晰：发什么由使用者按自己硬件填写，软件只负责"最高优先级发出 + 如实报告结果"。
- 代价：默认不可用（未绑定），需要使用者配置一次；必须用显式提示引导配置。

## 3. 决策内容 (Decision)

1. `EmergencyStop` = **一条保留的发送槽位**（每台会话一条），默认**未绑定**。
   绑定内容是一条自定义命令（文本/HEX，可含换行），随会话（`DeviceSession`）持久化。
2. **未绑定时**：按下空格键只弹出明确提示（"急停未绑定命令：请按你硬件的停机指令配置"），
   **不得发出任何字节**，也不得显示任何"已停机"字样。
3. **已绑定时**：走独立的最高优先级发送路径：
   - 跳过人工审批、`SafetyGuard` 限幅与冷却限制（急停本身就是极端动作，限幅会阻止它）；
   - 不排队等待周期性发送或写入冷却；
   - **不跳过物理现实**：端口未打开、写入未确认、设备无回执，都必须如实上报，绝不自动升级为"已停机"。
4. **结果三态**（界面与审计都必须用它，不允许二值化）：
   - `未送达`（端口未打开、写失败）；
   - `已发出，未确认`（无回执链路下的默认结论）；
   - `设备已确认`（仅在设备显式回执时）。
5. **审计**：每次触发记录时间、绑定名、实际字节、结果三态、是否由快捷键触发，标记 `emergency = true`；审计不可关闭。
6. **不自动重试**：一次触发一次发送；需要再次发送由人再按（避免把"自动重发"伪装成可靠机制）。

## 4. 影响与后续结果 (Consequences)

- **正面**：软件不假装懂硬件；急停能力对使用者开放；在无回执设备上不会造成"按了就等于停了"的误判。
- **负面 / 应对**：
  - 使用者必须配置一次才能用 → 首次连接会话时给出引导，并在未绑定状态下让空格键提示可发现；
  - 使用者可能配错命令（例如配成加速指令）→ 绑定界面显示将要发送的字节并要求确认；该槽位**只允许一条命令**，不允许脚本或多条串联。
- **必须保持的不变量**：
  1. 未绑定 ⇒ 零字节发出；
  2. 急停路径不参与自动重试与冷却排队；
  3. 结果永远是三态之一，且在设备无回执时不得显示"已停机"；
  4. 审计记录不可关闭、不可编辑。
